# Know-how｜把人審教案安全轉成可運作的 App 課程

## 1. 先決定資料模型，不要把變體硬塞進舊課

人類教案可以說「這是某課的變體」，但若 App 沒有變體 ID、入口與進度語意，硬塞進同一份 JSON 會讓使用者無法單獨開始、分享或辨識完成的是哪一段。

在尚未值得新增複雜模型時，可先把能力變體做成獨立延伸課，並用：

- summary 說明它和舊課的差異。
- prerequisite 連回真正的先備課。
- next 提供建議順序，不冒稱能力依賴。
- curriculum metadata 留下來源單元與系列。

等出現大量共用內容、同一課多段音訊或跨變體成績需求，再新增正式 variant schema。

## 2. 從 Markdown 搬到 JSON 時要重新做機器驗證

人審稿看起來正確，不等於資料可載入。正式內容至少要驗證：

- 句子 ID 連續，對話角色與雙語文字完整。
- 詞卡 surface 真正在引用句的完整字界出現。
- 理解題固定三個選項、答案索引有效、證據句存在。
- 任務每個 step 都有搭檔台詞、中文提示、關鍵字、句架與示例。
- 新 metadata 在 validator 有明確型別、數量與 enum 規則。

這些檢查應進 `npm run check`，而不是只在一次性轉檔腳本裡。

## 3. 口語自然化應是「可選層」，不是新的必背清單

初學者需要先確認清楚說法能完成任務。自然說法應：

- 預設收合，標示核心課後再開。
- 區分「可主動練用」與「先聽懂」。
- 說明語氣與適用情境，尤其俚語、熟人用語與正式場合差異。
- 不覆寫正式課文，也不成為第一次完成的必要條件。

短回應練習要有成功條件，避免只展示兩句看似自然的英文卻不知道在練什麼。

## 4. 裝置 TTS 可以先提供可用性，但標示必須誠實

若內容尚未製作完整固定聲音，可設定 `preGeneratedAudio: false`：

- 課程與口語點播使用裝置英文語音。
- audio manifest 不加入不存在的 lesson ID。
- UI 明示「裝置語音」與「尚未經真人聽評」。

這適合先驗證課程動線，不適合拿來證明數字最小對立、重音、弱讀或情緒自然。像 `nine / nineteen` 必須在固定音檔完成後再真人聽評。

## 5. 情境化標題與按鈕要使用同一資料來源

只把任務標題改成「室友說」還不夠；播放按鈕若仍寫「聽店員」，會立即破壞情境。標題與動作文字應由同一個 `partnerLabelZh` 推導，不要各自硬編碼。

UI 驗收要看完整互動面，不只確認資料欄位存在。本批正是在實際任務頁抓到自動測試原先沒有揭露的稱呼不一致。

## 6. 內容增加需要同步三種計數

新增課程後至少同步：

1. `content/index.json` 的課程與句子總數。
2. README 對外顯示的當前總數。
3. 測試對內建課程數量的明確斷言。

歷史 devlog 應保留當時數字，不要為了現在的 115 課，把過去驗收時的 111 課改寫成不存在的歷史。

## 7. 發布前還有一個音訊專案

正式固定音檔不是把 TTS 跑完就結束，至少要確認：

- 四個核心 voice sets 的每句檔案完整、manifest 順序一致。
- A/B 角色可辨、速度符合 L1。
- 數字、否定、`extra`、尺寸與顏色不因重音模糊。
- 自然說法與正式課文的語氣一致，但不讓選修音檔混入核心完成判定。

在這些條件完成前，保留 device-only 狀態比部署一套未聽評固定音檔更誠實。
